# SPEC.md

## Stack recommendation

**Vite + React 18 + TypeScript for the shell, imperative Three.js for the viewport, Zustand for state, Sass (SCSS) for styling.**

Why this split matters: a mesh editor mutates geometry dozens of times per second (dragging a gizmo re-runs an extrude solve every frame). React Three Fiber is excellent for declarative scenes, but reconciling a scene graph on every vertex change fights you constantly, and you end up escaping to refs anyway. So:

* **React owns the chrome**: toolbars, outliner, properties panel, modals, modifier stack. This is where React earns its keep, and where a brutalist design system is easy to express as components.
* **Three.js owns the canvas**, mounted once into a `<canvas>` via a ref and never re-rendered by React. It reads from the Zustand store and pushes selection changes back.
* **Zustand instead of Redux** because you need fine-grained subscriptions (the properties panel should not re-render when the camera moves) and non-React code needs to read state directly. `subscribeWithSelector` handles both.
* **Sass (SCSS)** for styling because the UI needs a structured design system with reusable components, design tokens, nesting, mixins, and predictable styles without introducing a utility-class framework.

Alternatives considered: Svelte is lighter and would work, but the Three.js ecosystem tooling and the pool of examples for React is much deeper. Vanilla TS keeps bundle size down but you rewrite panel state management by hand. Ship as a web app first; wrap in **Tauri** later if you want native file dialogs and a bundled converter (much smaller than Electron).

Libraries worth pulling in: `three-mesh-bvh` (fast raycasting for selection on dense meshes), `earcut` (n-gon triangulation), `lil-gui` only if you want a debug panel, `vitest` for kernel tests.

## Architecture

Split into two packages in a monorepo. This is the single most important decision for making the build agent-friendly and testable.

```text
/packages
  /kernel        pure TypeScript, zero Three.js imports
    mesh/        BMesh data structure (Vert, Edge, Loop, Face)
    ops/         extrude, inset, bevel, loopcut, knife, merge, ...
    modifiers/   mirror, array, subdivide, solidify
    io/          fbx-ascii.ts, obj.ts, gltf.ts
    commands/    command objects + undo stack

  /app
    viewport/    Three.js renderer, overlays, gizmo, camera controls
    ui/          React panels, brutalist component library
    store/       Zustand slices
    bridge/      kernel mesh -> BufferGeometry sync
    styles/      Sass design system and component styles
```

The kernel has no DOM and no rendering dependency, so every operation can be unit tested headlessly: build a cube, extrude face 2 by 1.0, assert 10 faces and 16 verts. That gives Claude Code a tight feedback loop instead of "looks right in the browser."

### Styling architecture

Sass should be organized as a small design system rather than scattered component styles.

```text
/app/styles
  _tokens.scss
  _mixins.scss
  _reset.scss
  _base.scss
  _typography.scss

  /components
    _button.scss
    _panel.scss
    _toolbar.scss
    _outliner.scss
    _property-panel.scss
    _modifier-stack.scss
    _status-bar.scss

  /layout
    _app-shell.scss
    _viewport.scss
    _tool-rail.scss

  main.scss
```

Use **CSS custom properties for runtime design tokens** and Sass for organization, mixins, shared calculations, and component composition.

Example:

```scss
:root {
  --void: #0b0b0b;
  --bone: #f4f1ea;
  --red: #e5342a;
  --oxblood: #7b1113;
  --rust: #b8452f;
  --ash: #1a1918;
  --grid: #3a2a28;
  --amber: #f2a03d;
  --cyan: #3de0d0;

  --border: 3px;
  --shadow-offset: 4px;
  --panel-gap: 8px;

  --font-display: "Archivo Black", sans-serif;
  --font-mono: "JetBrains Mono", monospace;
}
```

The Sass layer should provide reusable primitives for borders, offset shadows, focus states, panel headers, and active states without turning the UI into a collection of duplicated declarations.

Avoid introducing a second styling abstraction such as Tailwind, CSS-in-JS, or a component library unless a specific requirement emerges.

### Mesh representation

Use a BMesh-style structure (Blender's model), not raw triangle soup.

You need:

```text
Vertex { co, edges[] }
Edge   { v0, v1, loops[] }
Loop   { vert, edge, face, next, prev }
Face   { loop, normal, materialIndex }
```

Without adjacency, loop cut, bevel, and select-loop are all difficult or impossible to implement robustly.

Triangulation happens only at the display and export boundary.

### Display bridge

Each mesh maintains three GPU buffers rebuilt on dirty flags:

1. A triangulated solid mesh.
2. An edge line set.
3. A vertex point cloud.

Rebuild only the dirty submesh and keep typed arrays preallocated with slack.

### Command layer

Every mutation is a command object with `do` / `undo`.

For structural operations, snapshotting the whole mesh is simpler and fast enough under about 200k verts.

For transform drags, store only the delta.

Cap history at 64 steps.

### Agent/scripting API

Expose the kernel command set as a plain function API:

```ts
app.exec("extrude", {
  faces: [...],
  offset: 1.0
});
```

This gives you the test harness, the undo system, and a way for an external tool to drive the app, all from one surface.

# FBX export

This is the highest-risk part of the build, so it should be planned explicitly.

There is no native FBX exporter in Three.js and FBX is an Autodesk format.

The workable approach is an **ASCII FBX 7.4 (version 7400) writer** implemented in the kernel.

Unity, Unreal, Blender, Maya, and 3ds Max all provide support for ASCII FBX.

Binary FBX is a later optimization, not an initial requirement.

## FBX structure

The writer should emit:

* `FBXHeaderExtension`

  * FBXVersion 7400.
  * Creation timestamp.
  * Creator string.
* `GlobalSettings`

  * UpAxis.
  * UpAxisSign.
  * FrontAxis.
  * CoordAxis.
  * UnitScaleFactor.
* `Definitions`

  * Accurate object counts.
* `Objects`

  * One `Geometry` per mesh.
  * One `Model` per mesh.
  * Material nodes.
* `Connections`

  * Geometry → Model.
  * Model → root.
  * Material → Model.

## Import-critical details

Each of the following should have dedicated tests.

### Polygon index encoding

The final vertex index of every polygon is encoded as:

```text
-(index + 1)
```

Forgetting this causes polygon boundaries to be interpreted incorrectly.

### Normals, UVs, and materials

`LayerElementNormal`, `LayerElementUV`, and `LayerElementMaterial` must use matching:

* `MappingInformationType`.
* `ReferenceInformationType`.

Use:

```text
Normals:
ByPolygonVertex / Direct

UVs:
ByPolygonVertex / Direct

Materials:
ByPolygon / IndexToDirect
```

### Axis and units

Export options should support:

* Y-up.
* Z-up.
* Meters.
* Centimeters.

Provide presets:

* Unity.
* Unreal.
* Blender.
* Maya.

The user should not have to understand coordinate-system conventions to produce a valid export.

### UVs

Even without a texture pipeline, emit a UV layer.

Use box projection as the default.

This avoids downstream problems caused by missing UV data.

## Export options

Support:

* Apply modifiers.
* Apply transforms.
* Triangulate.
* Selection only.
* Smoothing.
* Per-vertex normals.
* Smoothing groups.
* Scale factor.
* Axis preset.
* Unit preset.

# Brutalist UI direction

## Design language

Use:

* Hard 90-degree corners everywhere.
* `border-radius: 0`.
* No exceptions.
* 2–3px solid black borders.
* Offset drop shadows.
* No blur.
* Exposed structure.
* Uppercase monospace labels.
* Visible dividers.
* No gradients.
* No glassmorphism.
* No soft visual states.

Buttons should visually shift by 2px when pressed so they meet their own offset shadow.

Panels should look bolted to the screen rather than floating above it.

# Usability guardrails

Brutalism should be visually aggressive without becoming difficult to use.

Requirements:

* Hit targets of at least 40px.
* Maintain WCAG AA contrast.
* Show active tool state through at least two channels.
* Never rely exclusively on color.
* Use a filled indicator bar for active tools.
* Keep a persistent hint line in the status strip during modal operations.
* Preserve clear keyboard focus states.
* Avoid animations that obscure state changes.

Brutalism should read as **loud and honest**, not as a puzzle.

# Highest-risk items

Prioritize technical risk in this order:

1. Knife tool robustness.
2. FBX ASCII correctness.
3. Bevel on complex vertex fans.
4. Boolean operations.

Knife and bevel should be scheduled after the core topology system is stable.

However, the FBX writer should be **prototyped early** against a hand-built cube.

The objective is to prove that the export format works before the entire modeling kernel is finished.

# Engineering principles

## Keep the kernel pure

The kernel must never import:

* React.
* Three.js.
* DOM APIs.
* Browser APIs.

It should be executable in Node and testable entirely through unit tests.

## Keep Three.js imperative

The Three.js scene should be initialized once.

React should not reconcile individual mesh vertices or scene graph objects.

React communicates with the viewport through the store and explicit bridge APIs.

## Keep React focused on UI

React owns:

* Panels.
* Forms.
* Toolbars.
* Outliner.
* Modifiers.
* Dialogs.
* Menus.
* Status information.

Three.js owns:

* Rendering.
* Camera.
* Gizmos.
* Selection raycasting.
* Viewport overlays.
* GPU resources.

## Keep state granular

Zustand stores should be divided into slices so that changes to:

* camera state,
* selection,
* active tool,
* scene objects,
* properties,
* modifiers,

do not cause unrelated components to re-render.

Use `subscribeWithSelector` where non-React systems need fine-grained subscriptions.

## Test the kernel, not screenshots

Every topology operation should have deterministic tests.

Example:

```ts
const cube = createCube();

extrude(cube, {
  faces: [2],
  offset: 1
});

expect(cube.vertices.length).toBe(16);
expect(cube.faces.length).toBe(10);
```

The browser should primarily validate integration and interaction.

The kernel tests should validate geometry correctness.

# Final architectural decision

The project should be built around four clearly separated responsibilities:

```text
                    ┌──────────────────────┐
                    │       React UI       │
                    │  Panels / Outliner   │
                    │ Properties / Tools   │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │       Zustand        │
                    │      App State       │
                    └───────┬───────┬──────┘
                            │       │
              ┌─────────────┘       └──────────────┐
              ▼                                    ▼
    ┌──────────────────┐                 ┌──────────────────┐
    │  Mesh Kernel     │                 │    Three.js      │
    │                  │                 │                  │
    │ BMesh            │◄───────────────►│ Viewport         │
    │ Operations       │     Bridge      │ Renderer         │
    │ Modifiers        │                 │ Gizmos           │
    │ Commands         │                 │ Selection        │
    │ Import/Export    │                 │ Camera           │
    └──────────────────┘                 └──────────────────┘
              │
              ▼
    ┌──────────────────┐
    │      Export      │
    │ OBJ / FBX / glTF │
    └──────────────────┘
```

**Core stack:**

> **Vite + React + TypeScript + imperative Three.js + Zustand + Sass (SCSS)**

The kernel remains framework-independent, Three.js remains isolated to the viewport, React handles the application chrome, Zustand coordinates state, and Sass provides the brutalist design system without Tailwind or another utility CSS framework.
